# Заготовка двосторонньої синхронізації з Google Calendar

Цей документ описує, як ми плануємо двосторонню синхронізацію задач
правої панелі-календаря з Google Calendar, і що вже зроблено в цьому PR.
У самому PR **немає OAuth, мережевих запитів і нового UI** — лише
інтерфейс, вимкнена заглушка, типи мапінгу поза моделлю задачі та тести.

## Що вже є в Super Productivity

Не вигадуємо синхронізацію з нуля. В upstream уже є кілька шарів:

1. **iCal / CalDAV як issue-provider**
   (`src/app/features/issue/providers/calendar`,
   `src/app/features/calendar-integration`,
   `src/app/features/schedule/ical`,
   плагін `caldav-calendar-provider`). Це переважно читання подій
   (iCal URL або CalDAV) і показ їх у планувальнику / розкладі.
   З події можна створити задачу.

2. **Bundled-плагін `google-calendar-provider`**
   (`packages/plugin-dev/google-calendar-provider/src/plugin.ts`,
   збірка в `src/assets/bundled-plugins/google-calendar-provider`).
   Уже вміє:
   - OAuth на пристрій (токен **не** їде в Super Productivity sync);
   - читати події з вибраних календарів (`events.list`, `singleEvents`,
     діапазон у тижнях);
   - двосторонні `fieldMappings` для назви, нотаток, `dueWithTime` /
     `dueDay` і оцінки часу;
   - створювати / оновлювати / видаляти подію;
   - auto time-block: коли задачі ставлять час, у календарі з’являється
     дзеркало з `extendedProperties.private.spTaskId` (локальна задача —
     джерело істини, дзеркало не імпортують назад, див. #8171);
   - повтор запитів при 429 і 403 `rateLimitExceeded` /
     `userRateLimitExceeded` (до 4 спроб, backoff);
   - коалесування записів time-block (~1000 мс) і обмеження паралелі (3),
     щоб не впертись у ліміт Google
     (`TimeBlockSyncEffects`).

3. **Як зараз зв’язується задача з подією.** Плагін пише в задачу
   `issueId` (формат `calendarId::eventId`), `issueProviderId`,
   `issueType` і `issueLastUpdated` (з поля `event.updated`). Ці поля
   є частиною моделі Task, отже потрапляють в **op-log** і на інші
   пристрої. Сам OAuth при цьому лишається локальним. Це працює для
   issue-provider, але погано масштабується як «справжня» двостороння
   синхронізація календаря: etag і службові id Google не повинні
   роз’їжджатися через журнал операцій.

Цей PR **не замінює** плагін і не вимикає його. Заглушка — окремий шар
для майбутньої синхронізації правої панелі, вирівняний з уже прийнятими
рішеннями плагіна (ідентифікатори, ліміти, time-block).

## Контракт заглушки

Код: `src/app/features/calendar-sync/`.

- `ExternalCalendarSyncProvider` — `connect` / `disconnect` /
  `pull(range)` / `push(changes)` / `status`.
- Типи події та лінка `ExternalCalendarTaskLink` (`externalId`, `etag`,
  `updatedMs`, `lastSyncedAt`) **поза** Task і op-log. Окремого сховища
  лінків поки немає — лише типи.
- `GoogleCalendarSyncStub` завжди в статусі `disabled`; методи нічого
  не роблять і не ходять у мережу.
- Токен `EXTERNAL_CALENDAR_SYNC` у DI зараз вказує на цю заглушку.

Складений `externalId` той самий, що в плагіні: `calendarId::eventId`
(`toCompoundExternalId` / `parseCompoundExternalId`). Це тимчасова
копія хелперів плагіна (G4): живий код імпортує їх з плагіна.

## Планований потік (не в цьому PR)

Наступна жива робота розширює bundled-плагін `google-calendar-provider`
(G3), а не окремий паралельний модуль. Нижче — той самий потік, із
виправленнями G1–G2.

1. **Підключення.** OAuth через уже наявний plugin-oauth, окремо на
   кожному пристрої. Без секрету в op-log. Заглушка `connect()` цього
   не запускає.

2. **Офлайн-черга.** Поки немає мережі (у користувача це 4–6 годин на
   день), `push` складає зміни в локальну чергу. Після появи зв’язку
   черга відтворюється. Кілька правок однієї задачі коалесуємо, як у
   time-block, і не шлемо більше ніж кілька паралельних запитів.
   Черга має бути **стійкою** (IndexedDB, переживає kill процесу,
   як чернетка quick-add), а не лише в пам’яті. Якщо задачу вже
   видалено, а upsert ще в черзі — upsert відкидаємо і ставимо в
   чергу видалення події, щоб вона не «воскресла» в Google (G5).

3. **Pull.** `events.list` за `timeMin`/`timeMax` видимого періоду
   панелі. Пропускаємо cancelled і події зі `spTaskId`, які ми щойно
   самі записали (захист від циклу, G2). Нові події стають задачами з
   `dueWithTime` або `dueDay` (all-day) за вже прийнятою моделлю часу
   SP. Id такої задачі — **детермінований** хеш від провайдера,
   календаря і події (G8), щоб два офлайн-пристрої не створили дубль.
   Pull **пропускає події, чиє видалення ще в офлайн-черзі**, щоб не
   воскресити щойно видалену задачу з тим самим id (G9). Для серій
   у ключ id входить також `originalStartTime` / `recurringEventId` (G7).
   Зв’язок task↔event зберігаємо в **синхронізованих даних** задачі
   / плагіна та в `extendedProperties.private` події (`spTaskId`), а не
   лише в локальному сховку (G1).

4. **Конфлікти.**
   - На стороні Google: `etag` (If-Match) і `updated` як ознака LWW
     самого API. 412 — перечитати подію, не затирати сліпо.
   - На стороні застосунку: **op-log лишається джерелом істини для
     локальної задачі**. `etag` можна тримати локально як підказку для
     If-Match; ідентифікатор зв’язку їде разом із даними задачі / плагіна,
     без окремого типу операції лише заради лінка (G1).
   - Якщо змінили і задачу, і подію під час офлайну: поля задачі
     залишаємо з op-log; лінк оновлюємо після успішного злиття, а не
     «останній timestamp перемагає в усьому».
   - Якщо нормалізовані поля не змінились, не пишемо op і не кличемо
     API (G2).

5. **Ліміти.** Повторити підхід плагіна: retry лише на 429 і 403 з
   причиною `rateLimitExceeded` / `userRateLimitExceeded`, експоненційний
   backoff, без ретраю інших 403.

## Зауваження рев'ю (G1–G5, G7–G9) і зміна плану

Цей PR і надалі **не містить runtime-коду** синхронізації. Нижче
виправляємо план документа, щоб наступна реалізація не пішла у
відомі пастки.

### G3 — не робимо паралельний модуль, розширюємо плагін

Заглушка `src/app/features/calendar-sync/` була задумана як окремий
шар «поряд» із bundled-плагіном `google-calendar-provider`. Це
дублювання: OAuth, `events.list` / insert / patch, time-block, retry
і `extendedProperties.private.spTaskId` у плагіні вже є.

**Наступна жива робота має розширювати саме плагін**, а не розводити
другий провайдер із тим самим Google API. Інтерфейс
`ExternalCalendarSyncProvider` у цьому PR лишається як контракт
для тестів і типів; підключати панель будемо до плагіна (або тонкої
обгортки над ним), а не до окремої реалізації. Новий UI «підключити»
і мережеві запити — у тому ж епіку, що й розширення плагіна.

### G1 — зв’язок task↔event має синхронізуватися між пристроями

Якщо мапінг живе лише на одному пристрої (локальний сховок лінків,
як було в попередній версії цього плану), другий пристрій після
pull створює дубль задачі для тієї самої події.

Тому відповідність зберігаємо в **уже синхронізованих даних**, а не
в локальній мапі:

- на стороні задачі — plugin/issue-дані задачі (або окреме поле в
  plugin persistence, яке їде в op-log / backup разом із задачею);
- на стороні Google — `extendedProperties.private` події
  (`spTaskId` уже використовує time-block плагіна).

Обидва боки потрібні, щоб pull на іншому пристрої впізнав уже
існуючу задачу і не створив другу. Службові `etag` можна тримати
локально як підказку для If-Match, але ідентифікатор зв’язку не
має бути прив’язаний до одного пристрою. Формат op-log не
розширюємо окремим типом операції лише заради лінка, якщо лінк
уміщується в дані задачі / плагіна.

### G2 — захист від циклу pull/push і від порожніх ops

Будь-яка двостороння синхронізація без сторожів зациклюється:
pull оновлює задачу → це знову push → Google змінює `updated` →
знову pull.

Правила для реалізації (у плагіні):

- Події з нашим `spTaskId`, які ми щойно самі записали, не
  імпортуємо назад як «нові» (як уже зроблено для time-block, #8171).
- Перед `push` порівнюємо нормалізовані поля (назва, час, тривалість,
  all-day). Якщо нічого не змінилось — **не пишемо op і не кличемо
  API** (немає no-op Update в op-log і немає порожнього patch).
- Після успішного pull, який лише вирівняв локальний стан під вже
  відому подію, теж не диспатчимо Update, якщо значення ті самі.
- `etag` / `updated` використовуємо як умову If-Match і як ознаку,
  що віддалена подія не змінювалась; вони не повинні самі по собі
  породжувати новий цикл.
- Коалесування й ліміт паралелі лишаються, як у time-block.

### G8 — детермінований id задачі з однієї події

Синхронізований лінк (G1) не рятує від гонки, типової для цього
користувача: подія вже є в Google, два пристрої кілька годин офлайн
одне від одного, кожен робить pull і створює задачу з **випадковим**
id. Після появи зв’язку в op-log виявляються дві різні задачі на одну
подію, обидві з лінком.

Тому id задачі, створеної з події, має бути **детермінованим**:
стабільний хеш від `provider + calendarId + eventId`. Для інстансів
повторюваної події додаємо ще `originalStartTime` (або instance id),
щоб різні входження не злились в одну задачу (див. також G7). Той
самий вхід на двох пристроях дає той самий task id, і Create в op-log
зливається як одна сутність.

Правила злиття, якщо все ж з’явились два різні task id на одну подію
(старий клієнт, або хеш рахували без instance key):

- Канонічною лишається одна задача: раніше створена з валідним лінком
  (або та, на яку вже вказує `spTaskId` події). Другу вважаємо дублем:
  не пушимо з неї другу подію в Google і не імпортуємо подію вдруге.
- Create з уже відомим детермінованим id — це upsert / no-op, а не
  друга задача (як сторож порожніх ops у G2).
- Дзеркала time-block з нашим `spTaskId` задачі не створюють (G2).

### G4 — не тримати другу копію toCompoundId

`toCompoundExternalId` / `parseCompoundExternalId` у цьому PR —
свідома копія `toCompoundId` / `parseCompoundId` плагіна, щоб не
імпортувати `plugin-dev` у бандл застосунку (заглушка в рантайм
програми не підключена). Коли розширюватимемо плагін (G3), живий
код має імпортувати хелпери з плагіна, а цю копію прибрати.

### G7 — recurrence і часовий пояс події

У моделі `ExternalCalendarEvent` потрібні поля для інстансів
повторюваних подій і для TZ, інакше детермінований id (G8) зіллє
різні входження в одну задачу, а час зміститься при іншому поясі.

Поля вже є в контракті заглушки (runtime ще не читає їх):

- `recurringEventId` — id серії (Google `recurringEventId`);
- `originalStartTimeMs` — початок цього входження, як у
  `originalStartTime` Google; входить у ключ id інстанса;
- `timeZone` — часовий пояс події (IANA), окремо від локалі пристрою.

Перший живий pull має їх заповнювати; без них G8 для повторень
неповний.

### G9 — pull не воскрешає задачу, чиє видалення ще в черзі

Детермінований id (G8) має зворотний бік: якщо задачу вже видалено
локально, а видалення події ще в офлайн-черзі, наступний pull знову
створить задачу з тим самим id.

Тому **pull пропускає події, чиє видалення ще в черзі** (локальний
delete задачі / події ще не відправлено в Google). G5 закриває
зворотний напрям: видалена задача не воскрешає подію через upsert у
черзі. Разом вони не дають «воскреслій» парі задача↔подія, поки
офлайн-черга не відіграється.

## Що навмисно не робимо зараз

- Немає UI, кнопок «Підключити» і запитів до `googleapis.com`.
- Не змінюємо модель Task, reducers і op-log у цьому PR.
- Не реалізуємо розширення плагіна тут — лише фіксуємо план.
- Не додаємо залежностей.

## Наступні кроки

1. Розширити `google-calendar-provider` (G3): спільний мапінг для
   панелі-календаря, не другий клієнт API.
2. Зберігати зв’язок task↔event у синхронізованих даних задачі /
   плагіна та в `extendedProperties` події (G1).
3. Рахувати id нової задачі з події детерміновано і злити дублі, якщо
   два лінки вказують на одну подію (G8).
4. Вставити сторожі циклу і no-op (G2) до першого живого pull/push.
   Офлайн-черга — стійка; видалена задача не воскрешає подію (G5).
   Pull пропускає події, чиє видалення ще в черзі (G9).
5. Під час розширення плагіна (G3) прибрати копію `toCompoundId` (G4)
   і заповнювати recurrence / TZ події (G7).
6. Після цього підключити праву панель і окремим кроком — UI
   підключення.
